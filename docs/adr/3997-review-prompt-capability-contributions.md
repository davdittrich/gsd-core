# ADR-3997: Review-Prompt Capability Contributions

- **Status:** Proposed
- **Issue:** [#3997](https://github.com/open-gsd/gsd-core/issues/3997)
- **Amends:** [ADR-894](894-capability-declaration-format.md) (registers a 13th canonical loop point, `review:pre`, and a `reviewer` agent-role); [ADR-857](857-capability-system.md) ("Loop Extension Points (the 12)" is now 13)
- **Related:** [ADR-2363](2363-capability-instruction-surface-trust.md) (instruction-surface disclosure — see Decision 3, a closed non-change), [ADR-2782](2782-reviewer-lane-capability-surface.md) (reviewer-lane capability surface; this ADR extends the *prompt content* reviewers receive, not lane selection/transport)

## Context

Capability-owned guidance already reaches the planner, checker, executor, and verifier through the loop-contribution system (`plan:pre` → `into: "planner"`, etc.). `/gsd:review` (and `/gsd:plan-review-convergence`, which delegates to it) had no such seam: `gsd-core/workflows/review.md` never called `gsd_run loop render-hooks <point>`, and no canonical point existed for it to call. A capability whose constraints reach every other role — e.g. a simplicity mandate that shapes what the planner writes — was invisible to the external AI reviewers judging the resulting plan. Reviewers could recommend changes that directly conflict with an active capability's own rules, because they never saw them.

Live repro against `next` at filing time: `loop render-hooks review:pre --raw` → `Invalid loop point: "review:pre"`; `review.md` contained no `render-hooks` call at all.

## Decision

### 1. `review:pre` — a 13th canonical point, orthogonal to the discuss→ship pipeline

`review:pre` is added to `CANONICAL_POINTS` (`scripts/gen-loop-host-contract.cjs`) and to every derived/parallel copy of that vocabulary (below). It is declared by a new `STEP_WORKFLOWS` entry, `{ file: 'review.md', step: 'review' }` — a **sixth host**, not a sixth pipeline stage. `/gsd:review` is invoked ad hoc (directly, or via convergence), against any phase state, not as a fixed step between `verify` and `ship`. `CANONICAL_POINTS` still records it as an ordered array (position: appended last) because the generator's shape requires a total order. That position is not cosmetic: `capability-validator.cjs`'s `POINT_ORDER` derives from `LOOP_HOST_CONTRACT` (whose order comes from each workflow marker's `points:` line, which mirrors this array), and `POINT_ORDER` indices drive consumes-satisfiability ordering (`tests/capability-registry.test.cjs`'s `CANONICAL_POINTS`-vs-`POINT_ORDER` test is the only guard on this order; `assertPointsCoverage` itself is set-based and never checks it). Appending `review:pre` last therefore models every host artifact (`SUMMARY.md`, `UAT.md`, …) as available at `review:pre` — which is directionally true (review happens after those steps produce their artifacts) but coincidental, not designed. It is inert today only because `validateConsumesGlobal` walks `cap.steps`, and `step` is not a wired kind at `review:pre` (Decision 3). A future capability-level `step` at `review:pre` would need this reassessed.

### 2. `reviewer` — a role exempt from the agent-reference cross-check, like `orchestrator`

Every other non-`orchestrator` role in the contract (`planner`, `executor`, …) maps to a `gsd-*` in-repo agent, and the generator cross-checks that the agent name actually appears in the declaring workflow. `reviewer` has no such agent: `/gsd:review` invokes **external** AI CLI transports (claude, gemini, codex, cursor, …), never a spawned `gsd-*` agent. `crossCheckRoles` (`gen-loop-host-contract.cjs`) exempts `reviewer`, for the same reason it already exempts `orchestrator` (the role is a host's own external-invocation surface, not a delegate to cross-check) — but scoped to `review.md` specifically (`role === 'reviewer' && fileName === 'review.md'`), not a blanket exemption like `orchestrator`'s. A future workflow declaring `agent-roles: reviewer` still gets the real cross-check.

### 3. The contribution seam: `kind: "contribution"` (no `into` filter — `review:pre` has only one role), rendered once into the non-trimmed instructions block — capability-trust posture unchanged

`review.md`'s dispatch line runs `gsd_run loop render-hooks review:pre --raw` inline, inside the `{...}` instruction itself, inside `## Review Instructions` — not as a bash-computed artifact referenced by a separate data-fill placeholder, the way `RUN_DIR` and the other `gather_context`-populated placeholders in this same template work. A `gather_context`-step fetch (`REVIEW_PRE_HOOKS_JSON=$(...)`) was tried first and removed: it was *dead* — nothing echoed the value and nothing downstream re-read it, since each bash block in this workflow runs as its own subprocess with no shared shell state — and, independently, it turned out to be accidentally load-bearing for `getWiredKinds` (`gen-loop-host-contract.cjs`, #3606) purely because it was the file's *only* `loop render-hooks review:pre` call site; deleting it as an obvious cleanup moved the credited region and silently zeroed coverage a second time. That is a real, regression-tested reason to remove the dead fetch. It is **not**, on its own, a reason the call site had to move *inside the prose instruction* rather than into a bash-computed file: `coveredKindsInRegion`'s window is generous enough (verified: a bash-assigned `REVIEW_PRE_HOOKS_JSON=$(...)` followed by a separate `kind == "contribution"` sentence several lines later is credited exactly like `plan-phase.md`'s `plan:pre` seam is) that the deterministic bash-then-reference shape every other host workflow uses would have worked too. The inline form was chosen for the simpler reason: it is one line instead of a bash block plus a placeholder, and `review.md`'s `build_prompt` template is otherwise entirely `{...}`-driven data-fills with no bash inside it — adding one would be the only exception. The trade-off is real, not free: every other `loop render-hooks <point>` call site in the repo has deterministic (bash) acquisition and LLM-mediated consumption only; this one has both acquisition and consumption mediated by the model, so a skipped or garbled dispatch line degrades silently to the same bytes as the correct no-op case, with no runtime signal. Acceptable for a first-party, actively-developed workflow file; worth revisiting with a bash-computed-file form if `review:pre` contributions become load-bearing for a capability's correctness rather than an enhancement.

The dispatch line also does **not** filter on `into == "reviewer"`: `gen-capability-registry.cjs` only harvests `contributions[]` inside its `role === 'feature'` branch, and `validateAgainstContract` pins `contribution.into` to one of the point's declared `agentRoles` — `["reviewer"]` alone for `review:pre` — so no other `into` value can ever reach `byLoopPoint['review:pre'].contributions`. The runtime filter is therefore a no-op — and it is worse than a no-op, for the same `getWiredKinds` reason: a same-segment `into ==` narrows credited coverage to zero (exactly the mechanism that protects against a hand-rolled single-target dispatch masquerading as generic coverage). An early draft of this dispatch line *did* carry `into == "reviewer"` and it silently zeroed `review:pre`'s covered-kinds set — `validateHooksWired` then rejected every capability declaring a `review:pre` contribution, the one thing this ADR exists to enable. `tests/review-capability-contributions.test.cjs`'s `getWiredKinds(ROOT)` assertion is the regression test for both failure modes; see the `gh-3997` comment above `review.md`'s `gsd:loop-host` marker for the in-line warning against re-adding either one.

That section becomes part of `PromptSections.instructions` (`src/prompt-budget.cts`), which `assemblePrompt` pushes unconditionally and `applyBudget` never trims — the identical mechanism the `#3301` plan-coverage manifest already relies on to survive per-lane budget trimming. No prompt-budget code changes were needed.

The `review` step's marker declares `produces:` empty, not `REVIEWS.md`. `review:pre` is a `:pre`-only point — no `review:post` exists — and `HOST_ARTIFACT_EARLIEST_POINT_IDX` (`capability-validator.cjs`) always treats a step's *last* `points[]` entry as its artifact-availability anchor. For a single-point step that last entry is `review:pre` itself, so declaring `produces: REVIEWS.md` would record the artifact as available *before* review runs — backwards. No point declares `consumes: REVIEWS.md` today, so this was inert either way, but an empty `produces` can't misrepresent a timing this model has no truthful index for.

**No new instruction-surface disclosure code is added.** `collectInstructionSurfaces` (`src/capability-trust.cts`, ADR-2363 Phase 1) classifies only the `skills` manifest field today — no `contributions[]`/`gates[]`/`steps[]` fragment at any of the 12 *existing* points goes through per-field disclosure; contribution text is disclosed wholesale as part of the manifest at install-consent time, uniformly across every point. Building review-specific disclosure now would (a) be a general ADR-2363-Phase-2 concern, not one specific to `review:pre`, and (b) create an inconsistency where reviewer contributions get *more* scrutiny than the planner/executor contributions already shipping today. `review:pre` contributions inherit the exact same treatment every other point's contributions already get — this is a decision to leave the surface exactly as consistent as it already is, not an oversight.

`promptChannel: "none"` lanes (e.g. `coderabbit`) are unaffected by construction: they never read the prompt/instructions file at all (`src/review-lane-descriptor.cts`), so a reviewer contribution — delivered only through that file — structurally cannot reach them. No lane-selection or transport code changes.

### 4. `/gsd:plan-review-convergence` needs no separate wiring

`plan-review-convergence.md` delegates to `/gsd:review` (`Run /gsd:review for Phase {PHASE}.`) rather than re-assembling its own reviewer prompt. Every convergence cycle already inherits `review:pre` contributions through that delegation; adding a second `render-hooks review:pre` call there would be redundant and risk a stale second copy.

## Alternatives Considered

1. **Hardcode a specific capability's guidance (e.g. Ponytail) directly into `review.md`.** Rejected: couples core to one optional capability and cannot generalize to any other capability-owned review constraint — the opposite of the loop-contribution system's purpose.
2. **A bespoke reviewer-guidance channel outside the loop-contribution system** (its own config key, its own ordering/consent/compat rules). Rejected against `choose-boring-technology`: the contribution system is the in-stack, already-battle-tested answer (two landed precedents: `plan:pre → planner`, `#3934`'s `quick.md` auxiliary host) — same activation, ordering, compatibility, and consent machinery, zero new complexity tokens.
3. **Host-specific runtime hooks (e.g. a subagent-start hook).** Rejected: `/gsd:review` invokes multiple external transports, not one host-native subagent path — a hook-based approach would be runtime-specific and incomplete.
4. **New per-point instruction-surface disclosure code scoped only to `review:pre`.** Rejected — see Decision 3: it would widen the trust model asymmetrically for one point while every other contribution-bearing point keeps today's (wholesale-manifest) disclosure. If ADR-2363 gains contribution-fragment classification, it should do so for all 13 points at once, not one at a time.

## Consequences

- **Additive, byte-identical no-op by default.** No active `review:pre` contribution → the rendered block is empty and the reviewer prompt is unchanged from before this ADR.
- **13 canonical points, not 12**, everywhere that vocabulary is mirrored: `gen-loop-host-contract.cjs`, `src/loop-resolver.cts` (`CANONICAL_POINTS_FALLBACK`), `scripts/gen-capability-matrix.cjs` (`LOOP_POINTS`), and `scripts/registry-schema.cjs` (`LOOP_POINTS`, consumed by `validate-registry.cjs`'s `interactions.loopExtensionPoints` schema check). All four were independently hardcoded 12-point arrays discovered during implementation; each needed the same one-line addition, or a capability declaring `review:pre` would have failed schema validation even though the loop-host contract itself accepted it. `gsd-core/bin/lib/capability-validator.cjs` (`POINT_ORDER`) was a fifth such array — instead of adding a line to it, it was changed to derive from `LOOP_HOST_CONTRACT` (already required in the same file for `HOST_ARTIFACT_EARLIEST_POINT_IDX`), closing one of the five copies rather than growing it to six.
- **A capability may now declare a `review:pre` contribution with `into: "reviewer"`** and expect it rendered into every `/gsd:review` invocation, including convergence cycles, without per-lane special-casing (except `promptChannel: "none"` lanes, which never receive prompt content of any kind).
- **`review:pre` cannot deliver `into: "orchestrator"` contributions.** The `review` step's `agentRoles` is `["reviewer"]` only — unlike every other step, it does not also publish `orchestrator`. A capability therefore has no way to contribute to the `/gsd:review` orchestrator itself (e.g. lane selection, extra artifacts) at this point. This is a deliberate scope boundary, not a byproduct: the filed scope was reviewer-prompt content only, and adding `orchestrator` support would be new surface with no current consumer. Widening `agentRoles` to include it later is additive and does not require a new ADR.
- **Forever-cost:** one more point/role row in the loop-host contract, the capability registry's `byLoopPoint`, and the conformance matrix. No new dependency, no new disclosure class, no per-lane adapter.
